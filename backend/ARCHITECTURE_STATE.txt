1. SYSTEM OVERVIEW
────────────────────────────────────────────────────────────────────────────────

Three-tier architecture:
  Frontend   → Next.js (App Router) — src/app/(dashboard)/**
  Backend    → Node.js / Express + TypeScript — src/
  AI Service → FastAPI / Python — app/

Communication:
  Frontend ↔ Backend:  REST over HTTP (JWT Bearer auth)
  Backend  ↔ AI:       Backend calls FastAPI at AI_SERVICE_URL (default: localhost:8000)
                        5-second timeout; all calls return null on failure (graceful degradation)
  Python   ↔ MongoDB:  NEVER. Python has no DB access. Express assembles all context per-request.
  Python   ↔ ChromaDB: Direct (PersistentClient). ChromaDB lives inside ai-service/chroma_db/
  Backend  ↔ Redis:    ioredis singleton (lib/redis.ts). All Redis ops fail-open (platform
                        runs without Redis, just without caching/queuing).

Tech stack:
  Backend: Express 4, Mongoose 8, TypeScript, JWT (jsonwebtoken), bcrypt, dotenv, Razorpay,
           ioredis, BullMQ, Winston
  Frontend: Next.js (App Router), Tailwind CSS, Lucide Icons, React Context, Framer Motion
  AI: FastAPI, Pydantic v2, ChromaDB, sentence-transformers (all-MiniLM-L6-v2, 384-dim),
      google-generativeai (Gemini), pydantic-settings, redis (async)

Startup requirements:
  1. initFormulaLoader() called at app.ts startup — loads all formula JSON into memory
  2. MongoDB connected before any request
  3. ai-service running separately (uvicorn app.main:app)
  4. For AI responses: AI_PROVIDER=gemini + GEMINI_API_KEY in ai-service/.env
  5. For formula embeddings: POST /api/mentor/ingest-formulas must be called once per subject
  6. Redis optional: docker compose up -d redis (caching + BullMQ queues degrade gracefully)
  7. GEMINI_API_KEY in backend/.env for PYQ-grounded question generation (Node.js direct call)
     Without it, system falls back to template-based generation — no crash.

Environment (backend/.env required fields):
  JWT_SECRET, MONGO_URI, AI_SERVICE_URL, PORT
  Optional: REDIS_URL, RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET,
            NODE_ENV, DEV_MODE, GEMINI_API_KEY

3. CORE MATH — FORMULAS AND SCORING
────────────────────────────────────────────────────────────────────────────────

All pure math lives in lib/studyUtils.ts (no Mongoose, no side effects).

Ebbinghaus Retention:
  retentionScore = 100 × exp(−ln2 / halfLife × daysSinceSeen)
  halfLifeForAccuracy:
    accuracy ≥ 90%  → halfLife = 21 days
    accuracy ≥ 75%  → halfLife = 14 days
    accuracy ≥ 60%  → halfLife =  7 days
    accuracy ≥ 40%  → halfLife =  3 days
    else            → halfLife =  1 day

Mastery Score (per topic):
  masteryScore = accuracy × 0.6 + retentionScore × 0.4
  (accuracy = percent correct on all attempts to that topic)

Forgetting Factor:
  forgettingFactor = 1 − retentionScore / 100
  (0 = fully retained, 1 = fully forgotten)

Adaptive Topic Weight (topicWeightService.ts):
  rawWeight = errorRate×0.35 + forgettingFactor×0.30 + recencyScore×0.20
              + (1 − masteryScore/100)×0.15 + trendPenalty×0.10
  weight = clamp(rawWeight, 0.05, 1.0)
  recencyScore: 1.0 if wrong in last 2 results; else max(0, 1 − daysSince/21)
  trendPenalty: max(0, −subjectTrend/50)   [subjectTrend = avg(last3) − avg(prior3)]

Study Phase (studyPhaseFor, from daysToExam):
  daysToExam > 120  → foundation
  daysToExam > 60   → consolidation
  daysToExam > 30   → intensive
  daysToExam > 15   → revision
  daysToExam > 0    → final
  daysToExam ≤ 0    → post-exam

Exam Calendar (EXAM_MONTH_DAY):
  jee / jee_main:     May 1
  jee_advanced:       May 20
  neet:               May 5
  cbse:               March 1
  Year: targetYear if set; else auto-compute from current month

Burnout Risk (burnoutRiskFor, active days in last 14):
  ≥ 11 → high | ≥ 8 → moderate | ≥ 5 → low | else → none

Phase Daily Minutes (PHASE_DAILY_MIN):
  foundation: 180 | consolidation: 210 | intensive: 270 | revision: 300
  final: 240 | post-exam: 60

Readiness Score (readinessService.ts):
  subjectScore = accuracy×0.40 + retentionHealth×0.30 + trendScore×100×0.15 + consistencyScore×0.15
  overall = avg(subjectScores) + min(10, streakDays) + burnoutPenalty
  burnoutPenalty: none→0, low→-2, moderate→-8, high→-15

Revision Priority Score (revisionService.ts):
  priorityScore = errorRate×0.55 + recencyBoost×0.30 + retentionDecayFactor×0.15

Roadmap ROI Score (roadmapEngine.ts):
  roiScore = examWeightage×0.40 + masteryGap×0.30 + forgettingFactor×0.20 + hasMistakes×0.10
  masteryGap = (100 − masteryScore) / 100
  hasMistakes = 0 or 1

Mistake Analysis Smart Revision Priority (mistakeAnalysisService.ts):
  score = totalMistakes×0.5 + recentMistakes×0.3 + recencyBoost + streakBonus
  recencyBoost: ≤1d→1.0, ≤7d→0.6, else→0.2
  streakBonus: consecutiveWrong≥3→0.5, ≥2→0.2, else→0

4. BACKEND SERVICES

topicWeightService.ts — computeTopicWeights(userId)
  Redis cache: key tw:{userId}, TTL 5min. Serialized as plain object (Map→Object.fromEntries),
  deserialized with new Map(Object.entries(cached)).
  1. Check Redis cache — return immediately on hit
  2. Load all Results newest-first
  3. Batch-load Tests for those results
  4. Compute subjectTrend per subject (avg last3 − avg prior3, needs ≥6 data points)
  5. Build per-topic stats: wrongCount, totalAttempted, recentWrong (idx < 2), lastSeenAt
  6. For each topic: compute Ebbinghaus retention, masteryScore, forgettingFactor,
     recencyScore, trendPenalty, rawWeight → TopicWeight
  7. Write result to Redis cache (fire-and-forget)
  Returns: Map<topic, TopicWeight>
  WARNING: This is the most expensive call (loads all results + tests). Never call redundantly.
           It is called by: plannerService, adaptiveTestService, roadmapService, analyticsService,
           readinessService (inline), revisionService (inline)

TopicWeight shape:
  { subject, accuracy, wrongCount, totalAttempted, errorRate, recentWrong, subjectTrend,
    daysSinceLastSeen, weight, suggestedDifficulty, retentionScore, masteryScore, forgettingFactor }

streakUtils.ts — updateStreak(userId)
  Updates User.currentStreak, longestStreak, lastActivityDate.
  Logic: lastActivityDate === today → no-op (already recorded).
         lastActivityDate === yesterday → streak++.
         older or null → streak = 1.
  longestStreak = max(existing, newStreak).
  Called fire-and-forget after test submission (resultService) and revision access (revisionController).
  A "preparation day" includes both tests and revision sessions.

resultService.ts — gradeAndSave(userId, testId, timeTaken, answers)
  1. Load Test, verify ownership
  2. Build O(1) answerMap from submitted answers
  3. Grade MCQ (exact option match) and numerical (exact number match) separately
  4. Apply marking scheme (test.marking.correct / .wrong); unattempted = no penalty
  5. Persist Result to MongoDB
  6. void invalidateUserCache(userId) — busts Redis cache for tw, roadmap, practice recs
  7. void updateStreak(userId) — fire-and-forget streak update
  8. void enqueueAnalyticsJob({type:'update-mistake-patterns'}) — BullMQ queue
  9. void enqueueAnalyticsJob({type:'update-question-performance'}) — BullMQ queue
  Returns: GradedResult (id, testId, totalScore, correct/wrong/unattempted, accuracy, subjectWise)

testGenerator.ts — generateTest(req: GenerateTestRequest)
  Inputs: exam, subjects, chapters?, difficulty, questionCount?, cbseClass?, topicWeights?, adaptiveMode?
  1. Get config from EXAM_CONFIG (maxQuestions, duration, marking)
  2. Load topicPool from syllabusLoader
  3. Allocate questions per subject (NEET: Biology gets 50%; others: equal)
  4. Per subject: if topicWeights provided → weightedDistribute; else → equal distribute
  5. AdaptiveMode boosting:
     weak-topic:   masteryScore < 50 → weight ×2, else ×0.5
     revision:     forgettingFactor > 0.5 → weight ×2, else ×0.6
     surprise:     all weights → DEFAULT_WEIGHT (0.3, equal)
     balanced-mock / exam-adaptive: weights as-is
  6. JEE exams: ~20% numerical questions per topic slot
  7. Per slot: fillSlotFromBank() → bank first; if remaining > 0 → generateFallbackQuestions()
     (was: generateQuestions() template directly; now: Gemini-grounded → template only if Gemini fails)
  8. Shuffle all questions before returning
  Returns: GeneratedTest (questions are embedded in Test document when saved)

  generateFallbackQuestions(exam, subject, topic, topicType, difficulty, type, count, marks)
  → calls generateGroundedQuestions() from geminiQuestionGenerator.ts
  → logs source: 'gemini-grounded' | 'template-fallback' + pyqsInjected count
  → returns Question[] compatible with existing pipeline

mistakeAnalysisService.ts — updateMistakePatterns(userId, resultId)
  Classification rules (per wrong answered question):
    consecutiveWrong ≥ 3          → 'repeated'
    qType === 'numerical'         → 'formula'
    isMarked (flagged + wrong)    → 'guessing'
    timePressured                 → 'time-pressure'  (timeTaken < 60% of allowed)
    difficulty=easy + acc ≥ 65%  → 'careless'
    difficulty=medium + acc < 50% → 'weak-retention'
    else                          → 'conceptual'
  Runs as fire-and-forget. Batch-upserts MistakePattern per topic.
  Resets consecutiveWrong to 0 for topics answered correctly.
  Links formula chapter via findChapterByName if not already linked.

analyticsService.ts — getUserAnalytics(userId, full = true)
  Fetches results + User model (for streak data) in parallel.
  overview now includes: testsTaken, avgAccuracy, bestAccuracy, currentStreak, longestStreak.
  currentStreak: prefers User.currentStreak (counts tests + revisions); falls back to
                 computing from result dates only if User doc unavailable.
  longestStreak: from User.longestStreak.
  Full plan computes: overview, trends (last 10 results), subjects with trend delta,
  weakTopics (top 10, masteryScore ASC), strengths (acc ≥ 75% + attempted ≥ 3, top 8),
  questionTypes breakdown, activity (90d), recommendations, revisionRoadmap,
  calls aiServiceClient.analyzePerformance()
  Free plan: overview, trends (last 3 only), subjects, activity, lastTest only
  computeSubjectTrends: needs ≥ 6 data points; returns avg(last3) − avg(prior3)

5. PYQ GROUNDING PIPELINE (added in PYQ grounding phase)
────────────────────────────────────────────────────────────────────────────────

PURPOSE: PYQ datasets act as academic grounding/reference intelligence for all
Gemini generation. Gemini sees real exam style/depth/wording patterns before
generating questions, notes, mentor explanations, or revision plans.

DATA SOURCE:
  backend/src/data/pyqs/
    jee-main/   2019.json … 2024.json (JEE Main PYQs)
    jee-advanced/ 2019.json … 2024.json (JEE Advanced PYQs)
    neet/       2021.json … 2025.json (NEET PYQs)
  Each file: { questions: [{ questionId, subject, chapter, topic, difficulty,
               questionType, questionText, options{A,B,C,D}, correctAnswer, exam, year }] }
  Diagram-required questions are EXCLUDED from grounding (cannot be prompt-represented).

lib/pyqRetrieval.ts — PYQ Retrieval Library
  In-memory index: examFolder → subjectLower → chapterLower → PYQSlim[]
  PYQSlim: { exam, year, subject, chapter, topic, difficulty, type, text(≤350chars), options? }
  correctAnswer is NEVER included in PYQSlim — prevents Gemini from memorising answers.
  Lazy-loads per file on first access; idempotent (loadedFiles set).
  getRepresentativePYQs(exam, subject, chapter, topic?, limit=4) → PYQRetrievalResult
    Matching priority: exact chapter → fuzzy chapter (chapterSimilarity score ≥ 30) → subject-level
    selectVaried(): distributes across easy/medium/hard buckets for diversity
  getMultiChapterPYQs(exam, subject, chapters[], perChapter=2) → aggregated
    Cap: 6 chapters max to prevent token budget overflow.
  formatPYQsForPrompt(pyqs[]): formats as labeled blocks with header + text + options
  All retrieval logged via logger.debug with matched chapter and count.

lib/groundingContext.ts — Grounding Context Builder
  buildGroundingContext(params: GroundingParams) → GroundingContext (async)
    Combines: PYQ examples (via pyqRetrieval) + formula snippets (via formulaLoader)
              + syllabus units (via syllabusLoader) + exam style note
    GroundingContext: { pyqExamples, pyqText, formulaSnippets, syllabusUnits,
                       examStyleNote, debugLog: GroundingDebugLog }
    GroundingDebugLog: { buildTimeMs, pyqsFound, pyqsSelected, pyqSources[], formulasFound,
                         formulasUsed, syllabusMatched, syllabusUnits[] }
  serializeForPrompt(ctx) → compact text block injected before Gemini task instruction
    Format: === EXAM STYLE === | === KEY FORMULAS === | === SYLLABUS CONTEXT ===
            | === REPRESENTATIVE PYQ EXAMPLES (style reference — do NOT copy) ===
  buildMultiChapterGrounding(exam, subject, chapters[], pyqPerChapter) → combinedContext
    For full mock generation spanning multiple chapters.

  EXAM STYLE NOTES (injected into every prompt):
    JEE_MAIN:     Single correct MCQ + NAT. Balanced conceptual+numerical. 30/50/20 split.
    JEE_ADVANCED: Multi-correct, paragraph-sets, integer type. Deep multi-step. 10/45/45 split.
    NEET:         Single correct MCQ only. NCERT-grounded. Speed-focused. 40/45/15 split.

services/geminiQuestionGenerator.ts — Gemini-Powered Question Generator
  Uses @google/generative-ai SDK (gemini-1.5-flash, temp=0.7, topP=0.9, maxTokens=4096)
  Lazy-initialised from GEMINI_API_KEY env variable.
  generateGroundedQuestions(params: GeminiGenParams) → GeminiGenResult
    1. buildGroundingContext() with pyqLimit=min(4,count+1)
    2. serializeForPrompt() → groundingText
    3. computeDifficultySlots(count, exam, difficulty) → exam-specific difficulty distribution
    4. buildGenerationPrompt() → full Gemini prompt with grounding + task + JSON schema
    5. Call model.generateContent() with 25s timeout (Promise.race)
    6. parseGeminiResponse() → filters valid questions (type/options/correctOption checks)
    7. hydrateQuestion() → Question objects with UUID, conceptTags, formulaTags, subtopic
    8. If count > valid questions: pad remainder with template generator
  Falls back to templateFallback() on: missing API key, Gemini error, 0 valid questions parsed
  GeminiGenResult.source: 'gemini-grounded' | 'template-fallback'
  GeminiGenResult.debugLog: { exam, subject, topic, requestedCount, generatedCount, source,
                               groundingDebug, promptTokensEst, latencyMs, error? }
  Generated questions include: conceptTags[], formulaTags[], subtopic — enriched metadata
    that template-generated questions lack. These enable better explanation caching.

INTEGRATION INTO SERVICES:
  testGenerator.ts: fallback path (bank miss) → generateFallbackQuestions() → Gemini generator
    (was: direct template call; now: Gemini → template fallback)
  notesService.ts: buildGroundingContext() before aiServiceClient.generateNotes()
    Passes pyq_context + syllabus_context. Logs pyqsInjected + pyqSources.
  mentorService.ts: buildGroundingContext() when chapter+subject known before aiServiceClient.mentorChat()
    Passes pyq_context + syllabus_context on MentorChatRequest. Non-fatal if fails.
  revisionService.ts: getMultiChapterPYQs() before aiServiceClient.generateRevision()
    Passes pyq_context with 5 most relevant examples across top revision topics.

AI SERVICE CLIENT EXTENSIONS (all optional, backward-compatible):
  AiNotesRequest:       + pyq_context?: string | syllabus_context?: string[]
  AiRevisionRequest:    + pyq_context?: string
  MentorChatRequest:    + pyq_context?: string | syllabus_context?: string[]
  ConceptGuidanceRequest: + pyq_context?: string
  Python service ignores unknown fields if not updated — no breakage.
  When Python service is updated to consume these, grounding becomes end-to-end.

DEV/DEBUG ENDPOINTS (DEV_MODE=true only):
  POST /api/dev/grounded-generate
    Body: { exam, subject, chapter, topic?, type?, count?, difficulty?, showPrompt? }
    Returns: { groundingDebug, pyqsRetrieved, pyqRetrievalLog, generationSource,
               generationDebug, questions[], promptPreview? }
    Use: inspect exactly which PYQs/formulas were injected + see generated questions.
  POST /api/dev/grounded-full-test
    Body: { exam, subjects?, chapters?, questionCount?, difficulty? }
    Returns: { test, sourceBreakdown{fromBank,geminiGrounded,templateFallback}, latencyMs, questions[] }
    Use: end-to-end test of the grounded mock generation pipeline.

TOKEN BUDGET DISCIPLINE:
  pyqLimit default: 4 questions per chapter (≤ 1400 chars each)
  formulaLimit default: 8 formula strings
  PYQ text: truncated to 350 chars per question, options 120 chars each
  Target: ~800–1200 additional tokens per generation request for grounding context

14. KNOWN ENGINEERING RULES AND INVARIANTS
────────────────────────────────────────────────────────────────────────────────

1. req.user?.userId — ALL controllers use this field. req.user?.id does not exist.
   TokenPayload: {userId, email, plan, ...}. Forgetting this causes silent undefined auth.

2. computeTopicWeights() is expensive. Results are now Redis-cached (5min TTL).
   Still avoid calling redundantly in the same request.

3. updateMistakePatterns() and updateStreak() must always be fire-and-forget (void).
   Never block request response with these calls.

4. formulaLoader must be initialised via initFormulaLoader() before any formula API call.

5. Python never reads MongoDB. Express assembles StudentContextPayload per AI call.

6. api.get/api.post from lib/api.ts is the ONLY frontend API client pattern.
   Do NOT use authFetch — it is not exported from lib/auth.ts.

7. All Redis operations must fail-open. The platform must work without Redis.
   Never let Redis errors surface as user-facing 5xx responses.

8. ChromaDB returns distances (not similarities). Convert: score = 1.0 − distance.

9. MentorSession.messages uses $slice: -20 to keep rolling window. Never manually trim.

10. BullMQ inline fallback: enqueueAnalyticsJob falls back to inline sync execution
    when Redis is unavailable, so analytics never silently drop.

11. Map serialization for Redis: serialize as Object.fromEntries(), deserialize with
    new Map(Object.entries(cached)). Never JSON.stringify a Map directly.

12. Mastery bucket for explanation cache: Math.floor(mastery / 10) * 10 — students
    with similar mastery share cached explanations.

13. Streak tracking: lastActivityDate stored as Date (no time component compared).
    A day boundary is YYYY-MM-DD string comparison (ISO slice). Covers tests + revisions.

14. body has NO overflow-hidden in root layout. Dashboard self-contains its scroll
    via h-screen + overflow-hidden on its own wrapper. Don't add overflow-hidden to body.

15. PrepInsightGate fires prep_insight_gate_shown on mount via useEffect. Always wrap
    in AnimatePresence for smooth enter/exit animation.

16. PYQ grounding context is assembled synchronously from in-memory index — never blocks.
    Only geminiQuestionGenerator.generateGroundedQuestions() is async (network call to Gemini).
    All grounding calls are non-fatal: always fall back gracefully, never throw.

17. correctAnswer is NEVER exposed in PYQSlim objects used for grounding. The model sees
    question text + options only — style/depth reference, not memorised answers.

18. GEMINI_API_KEY in backend/.env is for direct Node.js → Gemini calls (question generation).
    Python ai-service has its own GEMINI_API_KEY — they are independent keys.
    Both must be set if both paths are used.

19. Exam personality in prompts: JEE_ADVANCED uses dense conceptual phrasing, NEET uses
    direct NCERT-register, JEE_MAIN uses balanced register. Always include exam name in
    generation prompts — Gemini style adapts noticeably to this context.

20. /api/dev/grounded-generate and /api/dev/grounded-full-test require DEV_MODE=true.
    These endpoints are the primary quality-verification flow for grounded generation.
    showPrompt:true in grounded-generate returns the full Gemini prompt for inspection.

15. CURRENT ENGINEERING GAPS
────────────────────────────────────────────────────────────────────────────────

1. computeTopicWeights called multiple times per complex request (planner calls
   readinessService, adaptiveTestService, and roadmapService each of which may call it).
   Redis cache mitigates this in practice but a proper fix is to pass precomputed
   Map<string, TopicWeight> through service call chains.

2. Roadmap data only covers JEE_MAIN. No weightage file for NEET or CBSE chapters.

3. questionGenerator.ts still exists as template fallback for when Gemini is unavailable.
   Gemini-grounded generation (geminiQuestionGenerator.ts) is now the primary fallback path.
   Quality gap remains: template questions are generic; Gemini quality depends on GEMINI_API_KEY.

4. Formula embeddings are not auto-seeded. POST /api/mentor/ingest-formulas must be
   called manually per subject to seed ChromaDB.

5. AI provider is "mock" by default. Must set AI_PROVIDER=gemini + GEMINI_API_KEY.

6. MentorSession identifiedWeaknesses[] is populated but never automatically updated
   from Gemini responses. Update path from Python to Express not implemented.

7. No test for duplicate topic-to-chapter fuzzy matching edge cases in roadmapEngine.

8. Percentile estimates in readinessService are heuristic approximations, not real data.

9. ai-service has no authentication. Firewall from external access in production.

10. Product analytics events are logged to Winston only — no aggregation dashboard or
    database storage yet. Events are ephemeral log lines.
